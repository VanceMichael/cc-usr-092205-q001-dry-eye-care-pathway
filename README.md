# 干眼风险分层随访

支持企业职业健康中心与医院之间的干眼筛查、**版本化风险分层**、复查转诊和
**跨机构连续照护**：员工把异物感、视力波动误当普通疲劳、自行滴药掩盖炎症或
角膜风险的问题，在记录层面被可追溯地拦住。

## 领域关切如何落地

| 关切 | 实现 |
| --- | --- |
| 系统要按**当时有效**的分层规则给建议 | `fixtures/rules.json` 存放带生效区间的规则集（v1：2025-01-01 起；v2：2026-09-01 起）。`src/rules.py` 按评估日期选择规则，结论锁定规则版本、命中规则与事实依据 |
| 补报症状/换药/准备近视手术**只追加、不改旧结论** | `src/records.py` 的只追加时间线：新事件只往后写，新结论以 `supersedes` 接续旧结论；事件与结论均为哈希链，`verify()` 可发现任何对旧记录的篡改 |
| 七类事实组织成连续记录 | 问卷、工作环境、眨眼与用眼习惯、既往疾病、长期用药、泪膜检查、医生判断各为一种事件类型；新报告按“事实组”整组替换旧报告，避免数月前的旧症状污染当前判断 |
| 企业筛查转医院**不重复建档** | `src/identity.py`：同一证件令牌确定性自动挂接；无令牌但人口学信息一致时先“待核实”，工作人员核验证件后才合并，防止把两个真人错并 |
| 雇主只得群体风险、个体信息须本人授权 | `src/access.py`：医护跨机构调阅需本人就该用途授权（可撤回、留痕）；雇主角色访问个体记录一律拒绝；群体分布对不足 5 人的高危小格向上合并隐匿，无法用大桶相减反推个人 |
| 医护看清升级原因、处理经过、何时必须停药 | `src/care.py` 的 `review_narrative()` 输出升级史（含每次升级的规则版本与事实依据）、处理时间线、“停止自助用药”明确节点 |
| 患者收到与自身风险相符的提醒 | `patient_reminders()` 按本人最新层级与具体事实生成：紧急级要求立即停激素眼药水并就诊，低风险者只收到用眼休息与“无需特殊用药”，而非千篇一律 |

## 风险层级

`lifestyle` 生活干预 → `review` 2–4 周复查 → `medical` 1 周内眼科就医 →
`urgent` 24–72 小时内急诊。命中多条规则时取最高层级，处置建议随层级给出。

v2 相对 v1 的变化（缩血管眼药水与近视手术诉求升为就医级、盯屏阈值 8h→6h 等）
记录在规则文件的 `changes_from_v1` 中；规则变化**不追溯**——例如同一人 8 月在
v1 下为“复查”，9 月 v2 生效后因手术诉求升为“就医”，8 月那条旧结论保持不变。

## 端到端样例

`fixtures/scenario.json` 为全部合成的演示数据（无真实个人信息），主线人物王磊：
企业筛查（v1 复查）→ 症状持续≥14 天且自用缩血管眼药水（v1 就医、转诊）→
凭本人授权在医院接诊、诊断 MGD → 按医嘱停药后好转降级 → v2 生效后因近视手术
诉求再升级 → 网购含激素眼药水后出现角膜损伤（v2 紧急就医、立即停药）。

运行演示（打印身份合并、病程回顾、差异化提醒与雇主群体视图）：

```bash
python3 -m src.scenario
```

## 资料约定

- `contracts/domain.schema.json` — 共享领域资料结构
- `contracts/rules.schema.json` — 版本化规则集结构（含递归 any/all 条件子句）
- `contracts/scenario.schema.json` — 端到端样例结构（身份、授权、事件、群体）
- `fixtures/domain.json` — 领域事实与约束
- `fixtures/rules.json` — v1/v2 两版分层规则与各层级处置建议
- `fixtures/scenario.json` — 跨机构连续照护样例
